# 工程规范

> 提交规范、推送流程与代码规范。CLAUDE.md「提交与代码规范（硬性）」小节指向本文件；规则冲突时以 CLAUDE.md 为准并同步修订。
> 工具强制（Prettier/ESLint）由 T0-06 落地；落地前本规范靠纪律遵守。

## 1. 提交规范

### tag 集合（固定六个）

| tag | 用途 | 吸收的 conventional commits tag |
|---|---|---|
| `feat` | 新功能（功能清单中的功能点） | feat |
| `fix` | 修复 bug | fix |
| `improve` | 内部质量改进（重构、性能、风格，不改变外部行为） | refactor / perf / style |
| `docs` | 纯文档变更（本仓库文档驱动，高频） | docs |
| `chore` | 脚手架、依赖、CI、构建等杂务 | chore / build / ci |
| `test` | 补充测试 | test |

不引入其他 tag。回滚用 `git revert`，消息由 git 自动生成，不算违规。

### 消息格式

```
tag(scope): 中文描述 (任务ID)
```

- **scope** 可选，取工作区名：`web` / `api` / `shared` / `importer` / `docs`；根级改动（monorepo 配置、CI、.gitignore 等）省略
- **描述** 用中文，一行说清做了什么
- **任务ID** 尾缀挂任务索引编号，使提交可反查任务；仓库级特殊提交（如首次提交）可省略

示例：

```
feat(web): 题目卡片组件 (T0-04)
fix(api): 健康检查路由 CORS 头缺失 (T1-01)
improve(shared): 蓝图时限推导去重 (T1-07)
docs: M0 设计规范初稿 (T0-02)
chore: 初始化仓库（脚手架与文档）(T0-01)
```

### 提交粒度

**一个拆片子任务 = 一个提交。** 子任务的代码改动与其强制要求的文档同步改动（功能清单、任务索引、CONTEXT.md、ADR）进同一个提交——「功能更新不同步文档视为任务未完成」落到提交层面。任务收口的状态翻转（如门禁确认后置「已完成」）也随该任务的收口提交。

## 2. 推送流程

| 规则 | 内容 |
|---|---|
| 分支模型 | **直推 main**，不建 feature 分支、不走 PR（单人 + AI 协作，PR 是纯开销） |
| 推前门禁 | 本地 `npm run check && npm run build` 通过才允许推送 |
| 推送时机 | 拆片子任务提交落盘后**立即推送** |
| CI 角色 | 事后门禁：推送后运行 check/build/test，坏了直接 revert |

### 触顶收尾（配额触达限额）

**只写回任务索引，不做任何 git 操作**（不提交、不推送）。写回内容与改到一半的文件留在工作区，由同机续跑（次日 09:50 定时任务）消化——续跑完成该子任务时，上次的写回随其提交一起进入。

### 恢复协议

机器故障丢失本地工作区时：在其他电脑从远端 pull 后**重做该子任务**（未提交改动不抢救）。因每个已完成的子任务都已推送，最多损失当前进行中的那一个子任务。

## 3. 代码规范

适用于全仓库（apps / packages / tools）与全部模型产出（kimi-k3 / glm-5.3 / glm-5.3-flash）。UI 视觉与样式规范归 M0 产出的 docs/design/设计规范.md，不在本文档。

### TypeScript

- 各工作区 tsconfig `strict` 全开（现状维持），新增工作区照此配置
- 禁 `any`：不确定类型用 `unknown` + 收窄；第三方缺类型处写针对性声明

### 命名

| 对象 | 约定 | 示例 |
|---|---|---|
| 文件名 | kebab-case | `healthz.ts`、`question-card.tsx` |
| React 组件 | PascalCase | `QuestionCard` |
| 类型 / 接口 | PascalCase | `ExamBlueprint` |
| 变量 / 函数 | camelCase | `deriveTimeLimit` |
| 常量 | UPPER_SNAKE_CASE | `MAX_ATTEMPTS` |

### 注释与标识符

- **注释中文、标识符英文**（与文档体系一致）
- 注释只写代码表达不了的约束与意图，不复述代码做什么

### 错误处理

- 不吞错、不裸 catch；API 层错误响应格式由 docs/架构设计.md 定稿（Hono 统一错误处理）
- 服务端发起 URL 请求遵守 CLAUDE.md 安全约束（仅公网 http/https、请求前校验 host）

### 测试

- 测试框架已定稿（T1-03，2026-10-08）：Vitest + @cloudflare/vitest-plugin（原 @cloudflare/vitest-pool-workers 的官方更名继任包）——API 集成测试在 workerd 内跑真实 D1 绑定与应用迁移，非 mock；`apps/api` 的 `test` 脚本为 `vitest run`（非交互，根脚本与 CI 均调用）
- 里程碑完成定义含「测试通过」（见工作流文档 §6）；测试中不出现可用凭据字面量（用 test-only 常量，见 CLAUDE.md 安全约束）

### 工具现状

- 强制门禁：`npm run check`（全工作区 tsc --noEmit）+ `npm run lint`（ESLint flat config，全仓 0 错 0 警）+ CI（install/lint/check/build/test）
- Prettier + ESLint 已由 T0-06 落地（2026-10-07）：根 eslint.config.js（typescript-eslint recommended + react-hooks，忽略 dist/.wrangler/node_modules/coverage/.zcode）+ .prettierrc/.prettierignore + 根脚本 lint/format；根 devDeps 含工具链专用 typescript@6.0.3（typescript-eslint 需要 JS 编译器 API，工作区 tsc 7.0.2 为 Go 原生版无该 API；各工作区类型检查不受影响）
- `npm run format` 已交付但暂不强制：执行会重排约 13 个文件（printWidth 100 经实测选定）；需要时统一执行一次并单独提交
- 测试现状（T1-03 起）：apps/api 20 个用例（认证集成 17 + 密码纯函数 3，经真实 worker 入口），`npm run test` 全绿；web/shared/importer 的 test 脚本暂为占位 echo
