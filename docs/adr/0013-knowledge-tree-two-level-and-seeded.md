# 0013 知识点树两级深度与版本化种子入库

日期：2026-10-25 · 状态：已采纳（M3 启动，用户按规划草稿建议基线放行）

## 决策

1. **知识点树业务上限定两级**：`knowledge_points` 只存「考点（parent_id 空）→ 知识点（挂考点）」两级，深度约束是业务规则由代码校验（schema 的自引用结构保留，不进库约束）。模块由 `module_id` 承载（CONTEXT 术语「模块→考点→知识点」的模块即既有 `modules`）。
2. **树定稿为 shared 版本化常量入 Git**（`XINGCE_KNOWLEDGE_TREE`，XINGCE_BLUEPRINTS 同款单一权威），树是自产知识资产而非爬取题库数据，不属 ADR-0004 禁入范围。
3. **入库循蓝图种子先例**（T2-01b）：importer 生成幂等种子 SQL（按 `module_id + code` upsert + 孤儿清理），并入 import.sql 且输出独立可执行的 knowledge.sql 供远端轻量执行；`code` 为幂等锚点，定稿后不再改义。

## 为什么

- 两级深度：知识点是打标与掌握度统计的单元，粒度受「27,362 题摊到每个知识点需数十至数百题」约束——更深的树只会摊薄样本；两级规模约 100–250 节点，人工可校对（F3-1 的「glm-5.3 生成草稿 + 人工校对」流程才可行）。schema 自引用不动，未来若确需三级再放开业务校验，无迁移成本。
- 树入 Git：树由领域知识 + 真题抽样生成、经用户校对定稿，是可版本化演进的自产资产；入 Git 使树变更走正常提交评审，打标等下游按 import_runs 版本判断是否重打。
- code 锚点：打标（AI 子代理输出 qid→知识点映射）与种子入库都依赖稳定标识；名称可在校对中修改而 code 不变，避免重命名导致打标与掌握度数据失联。

## 后果

- 打标批量执行（T3-01b/c）以 code 为映射键；树结构变更（增删节点）经孤儿清理 + 重新打标生效，掌握度历史随 knowledge_points 行级联删除而消失（树定稿后应极少发生）。
- 远端种子在树校对定稿后执行一次；校对前的草稿树只入本地开发态。
